## 1. What ScienceBro is

ScienceBro is a local-first, AI-assisted computational research workbench.

Its purpose is to turn a scientific question into:

- a traceable literature corpus;
- explicit claims tied to exact evidence;
- falsifiable hypotheses;
- reproducible computational experiments;
- independent validation;
- a release-ready technical report, code repository, and data package.

ScienceBro is not an autonomous genius, a paper generator, or a substitute for domain expertise. Its main value is that it makes unsupported reasoning, hidden assumptions, missing citations, irreproducible experiments, and numerical failures visible.

The first scientific target is an independent audit of recently reported AI-discovered black-hole metrics from the AInstein project.

### Simple explanation

ScienceBro works like a factory with locked gates:

1. Find what scientists actually know.
2. Record exactly where each fact came from.
3. State what we think may be true and what would prove us wrong.
4. Run the experiment.
5. Make a separate validator attack the result.
6. Publish only what survives.

## 2. Success targets

### System MVP

A fresh clone of ScienceBro must support:

~~~text
uv sync
uv run sb doctor
uv run sb project status ainstein-audit
uv run sb dashboard
uv run pytest
~~~

The dashboard must open locally and show the real state of files in the repository. It must never invent progress.

### First research sprint

The first sprint must produce one of three honest outcomes:

1. Confirmation: at least one reported AInstein candidate passes independent invariant and numerical-convergence checks.
2. Refutation: a reproducible failure, artifact, or non-convergent region is found.
3. Inconclusive but useful: reproduction is incomplete, but ScienceBro releases a rigorous independent validator, failure map, or reproducibility report.

All three outcomes may be useful. Only the first two are potentially strong scientific claims.

### Longer-term target

ScienceBro should become a reusable template for computational research in:

- black-hole physics;
- gravitational waves;
- cosmology;
- astronomical anomaly discovery;
- AI-for-science evaluation.

## 4. System architecture

~~~mermaid
flowchart TD
    A["Human question"] --> B["Research engine"]
    B --> C["Evidence and claim ledger"]
    C --> D["Hypothesis and frozen protocol"]
    D --> E["Experiment engine"]
    E --> F["Independent validator"]
    F -->|"Fail or uncertain"| D
    F -->|"Pass"| G["Release gate"]
    G --> H["GitHub + DOI + preprint"]

    M["Zotero / files / Git history"] --- B
    M --- C
    M --- E
    M --- F
~~~

### Responsibilities

| Layer | Responsibility | Must not do |
| --- | --- | --- |
| Orchestrator | Route work and enforce gates | Declare a discovery |
| Research engine | Search, acquire, read, and compare sources | Treat web summaries as primary evidence |
| Evidence ledger | Connect claims to exact sources and locations | Hide uncertainty |
| Experiment engine | Execute frozen protocols and preserve outputs | Rewrite the hypothesis after seeing results |
| Validator | Attack claims with independent implementations and controls | Import the same code path it is validating |
| Dashboard | Display repository truth | Store secret state or manual fake percentages |
| Release gate | Check evidence, reproducibility, licensing, and disclosure | Publish automatically |

## 5. Scientific objects and vocabulary

ScienceBro must use explicit objects rather than relying on chat history.

### Research question

A narrow question with scope, significance, required inputs, exclusions, and a measurable completion condition.

### Evidence record

A source-backed observation containing:

- stable identifier such as DOI, arXiv ID, URL, or repository commit;
- exact source location such as page, section, equation, figure, table, or code line;
- short paraphrase;
- evidence type;
- strength and limitations;
- acquisition date;
- local file hash when a PDF is stored.

### Claim

A statement ScienceBro may want to use. Claims have states:

- speculative;
- source-supported;
- experimentally-supported;
- independently-validated;
- refuted;
- inconclusive;
- release-ready.

### Hypothesis

A testable proposition with:

- predicted observation;
- null hypothesis;
- falsification criterion;
- confounders;
- minimum experiment;
- planned analysis.

### Experiment

A frozen configuration, code version, command, environment, inputs, outputs, runtime, seeds, hardware record, and analysis plan.

### Validation

An independent attempt to break or reproduce an experimental claim.

### Artifact

A durable output such as code, a dataset, a checkpoint, a figure, a report, or a release bundle.

### Gate

A deterministic checklist controlling whether an object can progress to the next scientific state.

## 6. Mandatory scientific rules

These rules are non-negotiable.

### Evidence rules

1. Every externally factual scientific claim must have a source.
2. Prefer primary papers, official datasets, official documentation, and original repositories.
3. A search result, blog summary, LLM answer, or abstract-only reading is not full evidence.
4. Abstract-only evidence must be marked abstract_only: true.
5. Every citation used in a report must be verified against Crossref, arXiv, OpenAlex, Semantic Scholar, or the publisher.
6. Citation existence is insufficient: the cited location must actually support the claim.
7. Contradictory evidence must be preserved, not summarized away.
8. Missing evidence must remain visible as a blocker.

### Experiment rules

9. Freeze the hypothesis and primary metric before examining final results.
10. Preserve raw outputs as immutable artifacts.
11. Record Git commit, dependency lock, command, random seed, hardware, precision, and runtime.
12. Separate exploratory analysis from confirmatory analysis.
13. Never select only successful seeds or visually attractive runs.
14. Include negative controls and a known-answer baseline.
15. Numerical claims require convergence checks across resolution, tolerance, or precision.
16. Failures near boundaries, horizons, singularities, and excluded domains must be mapped explicitly.
17. A run completing without an exception is not scientific validation.

### Independence rules

18. The validator must not import the implementation being validated when an independent formulation is possible.
19. Upstream training loss is not an independent measure of correctness.
20. LLM-as-judge may evaluate formatting or workflow behavior, but not the truth of a tensor equation or numerical physics result.
21. Scientific pass/fail decisions should be deterministic or based on predeclared statistical tests.
22. The same agent may implement and debug, but a separate validation role must review the final claim and execute hidden checks.

### Claim rules

23. No claim is promoted because it sounds plausible.
24. Never use discovered, proved, novel, first, confirmed, or refuted without passing the corresponding gate.
25. A failed replication attempt is not a refutation unless the failure is shown to be methodological or intrinsic.
26. An absence of prior work after a search is written as no prior work was found under the documented search, not nobody has done this.
27. Uncertainty must be stated quantitatively where possible.
28. Claims must be downgraded automatically when their supporting evidence or validation becomes invalid.

### Engineering rules

29. Everything required for reproduction must be project-scoped and versioned.
30. Do not overwrite global Claude Code settings, user-level skills, or unrelated projects.
31. Inspect third-party installation scripts before execution.
32. Pin every external repository to a commit SHA.
33. Record licenses and attribution before copying code.
34. Never commit credentials, proprietary papers, or restricted datasets.
35. Execute untrusted AI-generated or third-party code in an isolated environment.
36. A clean clone must reproduce the documented baseline with one primary command.
37. Tests, linting, schema validation, and release checks must run in CI.
38. If a mandatory check cannot run, fail closed and display the blocker.

### Human gates

39. The human approves the primary research question.
40. The human approves promotion to a public scientific claim.
41. Submission to a journal or arXiv is always a deliberate human action.
42. Before a strong general-relativity claim is submitted, seek review from at least one qualified domain scientist when realistically possible.

## 9. Technology choices

### Core

- Python 3.12 for the ScienceBro orchestrator unless the inspected dependency set requires another compatible version.
- uv for environment and dependency locking.
- Pydantic for schemas.
- Typer for the sb CLI.
- Rich for terminal status.
- PyYAML or ruamel.yaml for human-readable configuration.
- Pandas and NumPy for result tables.
- Plotly for interactive scientific charts in the dashboard.
- Streamlit for the V1 local dashboard.

### Claude model routing

Use models deliberately rather than running the most expensive model for every edit.

- Fable 5 High: initial architecture, donor-system synthesis, difficult research design, major mathematical reasoning, and final adversarial review.
- Opus 5 High: normal implementation, debugging, tests, refactors, dashboard work, and most day-to-day experiment operations.
- Fable 5 High again: review before claim promotion or public release.

Recommended flow:

~~~text
Fable designs → Opus implements and iterates → Fable attacks the result
~~~

Manual switching is sufficient in V1. Do not build complicated automatic model routing before the research workflow works. A second model review may expose reasoning mistakes, but it does not replace deterministic scientific validation.

### Quality

- pytest;
- pytest-cov;
- Hypothesis for property-based tests where appropriate;
- Ruff;
- mypy or pyright;
- pre-commit;
- JSON Schema export from Pydantic;
- GitHub Actions.

### Scientific stack for the first project

Keep this in the AInstein project environment when possible:

- PyTorch or JAX according to upstream;
- NumPy;
- SciPy;
- SymPy;
- EinsteinPy only as an optional cross-check, not the sole validator;
- mpmath for selected high-precision tests;
- xarray for labeled grids if useful;
- matplotlib and Plotly;
- h5py, safetensors, or the upstream checkpoint format.

### Isolation

- Use Docker for untrusted upstream or AI-generated code when available.
- Support native execution for GPU performance after doctor checks.
- Never force Docker if it blocks the user's GPU; document the fallback.
- Each scientific project may have its own locked environment.

### Large data

Do not add infrastructure prematurely.

- Under roughly 100 MB: Git where licensing allows.
- Larger generated outputs: ignored local artifact directory plus manifests and hashes.
- Shared or released large artifacts: Zenodo, Hugging Face, or an official data repository.
- Add DVC only when data lineage actually requires it.

## 10. Claude Code agent roles

The main Claude Code session is the orchestrator. Specialist agents produce artifacts, not final authority.

### research-director

Purpose:

- narrow a vague topic;
- create a research question;
- define significance, novelty search, feasibility, and stop conditions;
- decide which specialist should act next.

Required output:

- QUESTION.md;
- search plan;
- initial claims needing evidence;
- list of assumptions;
- falsification-oriented project plan.

Forbidden:

- declaring novelty;
- writing a paper before evidence exists.

### literature-reviewer

Purpose:

- query academic databases;
- deduplicate papers;
- obtain full text;
- create evidence records;
- build citation and contradiction maps.

Required output:

- corpus.jsonl;
- bibliography.bib;
- reading notes;
- evidence records;
- unresolved source-access blockers.

Forbidden:

- inventing metadata;
- silently relying on abstracts.

### domain-critic

Purpose:

- attack the physics and mathematics;
- identify gauge, boundary, singularity, identifiability, and numerical issues;
- explain required concepts in plain language for the user.

Required output:

- domain assumptions;
- known-answer tests;
- adversarial checks;
- plain-language brief;
- external-expert questions.

Forbidden:

- pretending to be an accredited physicist;
- replacing deterministic calculation with verbal reasoning.

### experiment-engineer

Purpose:

- implement frozen protocols;
- isolate environments;
- run experiments;
- preserve raw artifacts and manifests;
- diagnose failures.

Required output:

- code;
- tests;
- run manifest;
- immutable raw results;
- logs;
- reproducible command.

Forbidden:

- changing the primary metric after seeing final data;
- hiding failed runs.

### independent-validator

Purpose:

- independently recalculate results;
- create hidden samples and negative controls;
- attack the claim;
- issue pass, fail, or inconclusive with reasons.

Required output:

- validation plan;
- independent implementation;
- validation report;
- failure maps;
- claim-state recommendation.

Forbidden:

- importing upstream loss or reusing the same critical implementation;
- judging based on narrative quality.

### release-reviewer

Purpose:

- verify claim-evidence alignment;
- verify citations, licenses, reproducibility, AI disclosure, and release completeness;
- prevent overclaiming.

Required output:

- release checklist;
- exact allowed wording;
- unresolved blockers;
- publication package manifest.

Forbidden:

- automatically submitting or publishing.

## 13. Dashboard specification

Build a simple local Streamlit dashboard. It is an instrument panel, not a decorative product.

Start command:

~~~text
uv run sb dashboard
~~~

### Page 1: Mission Control

Show:

- current project and exact research question;
- current discrete stage;
- next required action;
- blockers;
- latest verified artifact;
- last run time and Git commit;
- release readiness.

Use at most three summary indicators:

1. Evidence coverage: supported factual claims / all factual claims.

## 14. Research workflow

### Stage A: Intake

Output:

- narrow question;
- significance;
- scope;
- exclusions;
- available data and code;
- compute budget;
- success and stop criteria.

Gate:

- question is answerable by computation;
- at least one measurable result;
- no dependence on inaccessible data;
- one-week minimum artifact is possible.

### Stage B: Literature discovery

Search:

- exact topic;
- synonyms;
- foundational papers;
- newest papers;
- citations of the target paper;
- papers cited by the target;
- replication, comment, erratum, and critique terms;
- relevant code and datasets.

Output:

- deduplicated corpus;
- search log with queries and dates;
- paper ranking;
- access status;
- local full text where legal;
- bibliography.

Gate:

- key primary paper obtained;
- method-defining sources found;
- novelty search documented;
- missing sources listed.

### Stage C: Evidence extraction

For every important claim:

- create evidence record;
- record exact location;
- classify support, contradiction, or context;
- record limitations;
- require second-reader review for release-critical claims.

Gate:

- primary scientific background claims have evidence;
- target paper's exact claims are separated from ScienceBro's interpretations.

### Stage D: Hypothesis and protocol

Create:

- hypothesis;
- null;
- predicted result;
- primary metric;
- controls;
- thresholds;
- analysis;
- falsification criteria;
- compute budget.

Freeze before the confirmatory run.

### Stage E: Implementation

Requirements:

- known-answer unit tests;
- input schema validation;
- deterministic seed control;
- environment lock;
- run manifest;
- structured logging;
- checkpointing;
- raw-output preservation.

### Stage F: Experiment

Execute:

- known-answer baseline;
- candidate;
- negative control;
- hidden sample;
- precision/resolution variants;
- boundary stress tests.

Do not erase failed runs.

### Stage G: Independent validation

Use:

- separate mathematical formulation where feasible;
- separate sampling code;
- hidden points;
- perturbation controls;
- independent unit tests;
- convergence tests.

Decision:

- pass;
- fail;
- inconclusive.

### Stage H: Claim promotion

A claim may become independently-validated only if:

- evidence is traceable;
- experiment protocol was frozen;
- raw outputs exist;
- known-answer and negative controls pass;
- independent validation passes;
- limitations are recorded.

### Stage I: Release

Create:

- repository release;
- environment and reproduction instructions;
- result tables and figures;
- technical report;
- data availability statement;
- AI-use disclosure;
- Zenodo-ready bundle;
- arXiv-ready source if appropriate;
- author-contact summary.

## 15. First project: AInstein independent audit

### Project title

Independent Invariant Stress Test of AI-Discovered Black-Hole Metrics

### Target

Paper:

https://arxiv.org/html/2607.05489v1

Repository:

https://github.com/xand-stapleton/ainstein/tree/blackhole

### Plain-language question

The authors trained a neural network to produce geometries that approximately satisfy Einstein's vacuum equations and report black-hole-like candidates that differ from Schwarzschild.

We want to know:

Did the network find a genuinely interesting spacetime, or did it learn to look correct only under the authors' own loss, sampling, coordinate choices, or numerical precision?

### Primary research question

Do the reported candidate metrics remain vacuum-like, Lorentzian, black-hole-like, and non-Schwarzschild under an independent evaluator, unseen sample points, precision and convergence tests, and boundary/horizon stress tests?

### Important separation

Upstream answers:

- Can its own model minimize its own training objective?

ScienceBro must answer:

- Does an independently constructed evaluator verify the physical and numerical claims outside the upstream training path?

### Required baseline

Before testing a novel candidate, the independent verifier must correctly handle:

- Minkowski spacetime where applicable;
- Schwarzschild in the same or convertible coordinate convention;
- a deliberately perturbed non-solution;
- invalid-signature metrics;
- finite-difference or autodiff consistency on an analytic test metric.

### Independent checks

Implement or cross-check:

1. Metric symmetry and dimensional consistency.
2. Determinant and Lorentzian signature across the declared domain.
3. Inverse metric consistency.
4. Christoffel symbols.
5. Riemann tensor.
6. Ricci tensor.
7. Ricci scalar.
8. Einstein tensor or equivalent vacuum residual.
9. Kretschmann scalar and other curvature invariants.
10. Bianchi-related numerical consistency where meaningful.
11. Petrov speciality diagnostics or the exact invariant used by the paper.
12. Null expansions and trapped-surface diagnostics if the coordinate representation supports them.
13. Distance from Schwarzschild under the declared comparison and its gauge sensitivity.
14. Hidden-point residual sampling.
15. Horizon and domain-boundary failure maps.
16. Float32 versus float64 and selected higher-precision checks.
17. Grid/sample-density convergence.
18. Multiple seeds if compute allows.
19. Small parameter or checkpoint perturbations.
20. Cross-check between autodiff and an independent numerical or symbolic route on selected points.

### Residual normalization

Do not use a raw tensor norm without scale analysis.

Research and predeclare:

- tensor component normalization;
- coordinate dependence;
- characteristic curvature scale;
- absolute and relative residuals;
- behavior near zeros;
- excluded singular domains.

Calibrate thresholds using:

- analytic known solution;
- numerical discretization error;
- deliberately perturbed controls;
- precision sweep.

Thresholds may be set after baseline calibration but before inspecting final candidate results.

### Independence requirement

The verifier:

- may read exported metrics, coordinates, parameters, and checkpoints;
- may use upstream documentation;
- must not call upstream loss functions for the final pass/fail;
- must have tests that run without the upstream training package;
- must document any unavoidable shared dependency.

### Sprint schedule

#### Bootstrap: four to eight hours

- create ScienceBro MVP;
- pin donors;
- create AInstein project;
- fetch paper and repository metadata;
- run doctor;
- open dashboard;
- create evidence and hypothesis records.

#### Day 1: Reproduce the environment

- pin AInstein blackhole commit;
- inspect license and installation;
- build isolated environment;
- execute smallest documented example;
- record every dependency or code failure;
- run or reconstruct a known Schwarzschild case.

Exit condition:

- exact command and manifest exist;
- either baseline runs or a precise reproducibility blocker is documented.

#### Day 2: Export and interface

- identify candidate metric/checkpoint format;
- define neutral exported-metric interface;
- export one baseline and one candidate if available;
- build loader tests;
- prevent validator from importing upstream losses.

Exit condition:

- verifier can evaluate metric components at requested coordinates.

#### Day 3: Independent geometry core

- implement inverse metric, connection, curvature, Ricci, scalar, and residual;
- validate against analytic cases;
- compare autodiff and secondary method at selected points;
- create known-answer and perturbed controls.

Exit condition:

- all baseline scientific tests pass at predeclared tolerances.

#### Day 4: Candidate hidden-point audit

- sample unseen interior and exterior points;
- oversample horizon-scale and boundary regions;
- compute residual distributions and heatmaps;
- check determinant and signature;
- compare to controls.

Exit condition:

- raw results and initial failure map exist.

#### Day 5: Convergence and robustness

- precision sweep;
- sampling/grid sweep;
- multiple seeds or checkpoints where feasible;
- perturbation tests;
- gauge/comparison sensitivity review;
- curvature and trapped-region checks.

Exit condition:

- validator can distinguish real convergence, numerical floor, and obvious artifact.

#### Day 6: Independent review

- independent-validator reruns hidden checks;
- domain-critic attacks assumptions;
- evidence audit verifies all scientific background;
- claim ledger is updated;
- result is classified pass, fail, or inconclusive.

Exit condition:

- no release-critical claim is self-approved by its implementing role.

#### Day 7: Release candidate

- clean-clone reproduction;
- figures and tables;
- technical report;
- limitations;
- README;
- release checklist;
- Zenodo bundle;
- arXiv draft if justified;
- concise email package for upstream authors.

Exit condition:

- public wording exactly matches the claim gate.

### Minimum useful artifact

Even if the candidate cannot be reproduced, release only if useful:

- environment/reproducibility report;
- independent metric-verification package;
- known-answer test suite;
- failure diagnostics;
- exact blocker and upstream issue.

### Strong outcomes

#### Confirmation

Allowed wording:

We independently reproduced selected numerical properties of one reported AInstein candidate under the documented checks.

Do not say:

We proved a new black hole exists.

#### Refutation or artifact

Allowed wording:

We found a reproducible failure of claim X under check Y in region Z, and the failure does not diminish under the documented precision or resolution sweep.

Do not say:

The entire paper is fake.

#### Inconclusive

Allowed wording:

We could not independently resolve claim X because of blocker Y. We release the validator and exact reproduction record.

### Compute strategy

Home-computer target:

- one candidate;
- one known baseline;
- one perturbed control;
- hidden-point evaluation;
- limited precision and convergence sweep.

Scale only after the core validator works:

- more seeds;
- more checkpoints;
- denser grids;
- expensive higher precision;
- full candidate population.

## 19. Evaluation of ScienceBro itself

ScienceBro must improve through benchmarks, not through accumulating motivational instructions.

### Gold evaluation set

Create at least twenty small tasks over time:

- five literature retrieval tasks with known source sets;
- three citation-verification tasks including fabricated or mismatched citations;
- three claim-evidence alignment tasks;
- three contradiction-detection tasks;
- three computational reproduction tasks with known numerical results;
- two negative-control tasks;
- one complete mini-research task with a hidden conclusion.

The first five tasks may be created in V1. Grow to twenty after the AInstein sprint.

### Metrics

Track:

- citation metadata validity;
- citation-to-claim entailment;
- full-text usage rate;
- unsupported claim count;
- evidence coverage;
- experiment manifest completeness;
- clean-clone success;
- known-answer test pass;
- negative-control detection;
- hidden-check performance;
- cost;
- runtime;
- human correction count.

Hard release targets:

- zero fabricated references;
- 100% traceability for release-critical claims;
- 100% required manifest fields;
- clean-clone command documented;
- no hidden failed mandatory tests.

### Inspect AI usage

Use Inspect AI for:

- tool-selection behavior;
- research-agent task completion;
- citation workflow adherence;
- refusal to promote unsupported claims;
- regression tests after changing skills or prompts.

Do not use Inspect's model grader as the only scorer for scientific truth.

### Self-improvement protocol

When ScienceBro fails:

1. Save the failure case.
2. Classify retrieval, reasoning, coding, validation, or orchestration failure.
3. Propose a minimal rule, skill, adapter, or test change.
4. Add the failure to the eval set.
5. Run old and new evals.
6. Merge only if the new version improves the target without unacceptable regressions.
7. Record the decision.

Never allow an agent to silently rewrite CLAUDE.md, claim gates, or mandatory rules based only on its own self-assessment.
